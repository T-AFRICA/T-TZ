# Migrations

Forward-only, numbered SQL files. Destructive changes need explicit owner approval.
Applying them to the Supabase project is an owner action. As reported by the
owner on 2026-11-14, 0001-0003 are applied there; 0004 and 0005 are not yet.

| File | What it does |
|---|---|
| `0001_catalog.sql` | Catalogue tables and the storefront read model. |
| `0002_product_search.sql` | Trigram indexes and `search_products()`. |
| `0003_catalog_security.sql` | Row Level Security and explicit grants (anon/authenticated read the published catalogue only, nobody but the owner writes), security-invoker storefront view limited to active countries, `currencies` with each ISO 4217 exponent, price-currency check. |
| `0004_orders.sql` | Private `stock_levels`, `customer_profiles`, `orders`, `order_lines` with RLS (customers read only their own orders), `place_cod_order()` (reprice, stock check and reservation, idempotency key, one transaction) and `track_order()` (number plus email or phone). |
| `0006_order_admin.sql` | Order administration for the Central Admin: `order_status_events` and `order_notes` (private), and four functions executable by `service_role` only: list, detail, status change (one step forward at a time, cancel until dispatched with the stock put back, Cash on Delivery paid at delivery, the same request applied once) and internal notes. Customers and visitors get nothing new. Requires 0004. |
| `0007_payments.sql` | DRAFT, not applied anywhere: online payment records for an approved gateway. Orders may carry `mobile_money`, `card` or `bank_transfer`; private `payments` (amount and currency copied from the order, one payment in progress and at most one successful per order, TRONIC reference and the gateway's) and `payment_events` (every change and every refused attempt, codes only). Functions executable by `service_role` only: start (idempotency key), apply a verified gateway answer (allowed status changes, amount/currency/gateway/reference checks, each gateway event once; success marks the order paid and confirms it), expire (only waiting payments past their time), lookups for reconciliation. A customer reads the payments of their own orders, without the payer's number or the event log. Requires 0004. Not needed while Cash on Delivery is the only method. |
| `0008_deliveries.sql` | DRAFT, not applied anywhere: deliveries by TRONIC's own riders. Private `deliveries` (rider, six-digit customer code, wrong-code lock, cash collected), `delivery_proofs` (photo and signature, at most 1 MB each) and `delivery_attempts` (failed attempts with a reason). `service_role` functions: assign a rider (confirmed to packed; another rider until pickup), the rider's list and order (only orders given to that rider), the rider's steps (picked up, on the way, delivered with code, both proofs and the Cash on Delivery amount, failed attempt), the delivery and proofs for administrators (never the code). `customer_delivery_code()` for the customer (own order, or number plus checkout email or phone) while the order is on its way. Requires 0006. |
| `0009_admin_summary.sql` | DRAFT, not applied anywhere: `admin_country_summary()` (`service_role` only) for the Central Admin's country dashboard. Counts from the country's own records: orders (all, today in Africa/Dar_es_Salaam, open, by status), paid sales of orders placed in the last 30 days, customer accounts, products on sale, out of stock and low stock (5 or fewer). Nothing is estimated. Requires 0004. |
| `0010_rider_figures.sql` | DRAFT, not applied anywhere: `admin_rider_figures()` (per rider: orders with them, on the way, delivered today, in 7 and 30 days, failed attempts in 7 days, cash collected today, last delivery) and `admin_rider_deliveries()` (one rider's last 50 orders and failed attempts of 30 days), `service_role` only, never the customer's code. Requires 0008. |
| `0011_customer_admin.sql` | DRAFT, not applied anywhere: `admin_list_customers()` (website accounts, newest first, search by email, name or phone; each with their orders here, paid total, last order) and `admin_get_customer()` (one account with all its orders here), `service_role` only, read only. Requires 0004. |
| `0012_live_tracking.sql` | DRAFT, not applied anywhere: live order tracking. `deliveries.rider_phone` (copied from the rider's admin profile when the order is assigned) and private `delivery_locations` (latitude, longitude, accuracy, time; kept 7 days). `rider_report_location()` (`service_role` only: the assigned rider, only while the order is dispatched or on the way, at most one point every 10 seconds) and a 6-argument `admin_assign_delivery()` that also stores the rider's phone. `customer_order_tracking()` for the customer (own order, or number plus checkout email or phone): status history, and only while the order is on its way the rider's first name, phone and last 200 positions. Requires 0008. |
| `0013_delivery_point.sql` | DRAFT, not applied anywhere: private `order_delivery_points` (where the customer said their order should go, from their phone). `customer_set_delivery_point()` for the signed-in owner of a home-delivery order until it is delivered or cancelled (a new point replaces the old). Replaces `customer_order_tracking()`: never a rider name with an "@" (an order given to a rider without a name carried their email), plus the customer's point. Replaces `rider_get_delivery()`: the customer's point for directions while the order is not finished. Requires 0012. |
| `0014_claim_guest_orders.sql` | DRAFT, not applied anywhere: `customer_claim_guest_orders()` links the guest orders placed with the signed-in customer's verified email (`auth.users.email_confirmed_at`) to their account, so an order placed before signing in shows in the account. Never moves an order already linked to an account; an unverified address takes over nothing. Authenticated only. Index `orders_guest_email_idx`. Requires 0004. |
| `0015_orders_need_account.sql` | DRAFT, not applied anywhere: owner decision 2026-11-19, no order without an account. `place_cod_order()` is revoked from `anon` (the public key could otherwise place guest orders through the Supabase API) and granted to `authenticated` only. Tracking by order number plus email or phone stays open. Relies on Supabase Auth "Allow anonymous sign-ins" staying off. Requires 0004. |
| `0016_product_admin.sql` | DRAFT, not applied anywhere: products from the Central Admin (owner decisions 2026-11-20). `products.published_at` (draft / live / hidden; live is still `active`), private `product_image_files` (photos up to 1 MB, JPEG/PNG/WebP, in this database) and `catalogue_changes` (who changed what, one row per request). service_role-only functions: `admin_catalogue_options`, `admin_list_products`, `admin_get_product`, `admin_save_product` (create as draft or edit; the slug never changes), `admin_set_product_status` (live needs a price, a photo and a shown category; hide keeps everything), `admin_add_product_image` (12 at most), `admin_arrange_product_images` (order and remove; a live product keeps one), `admin_get_product_image`, `admin_set_product_stock`. `public_product_image()` for anon: photos of live products only, served by the storefront at `/media/products/<id>`. Requires 0004 and 0006. |
| `0017_inventory_admin.sql` | DRAFT, not applied anywhere: stock from the Central Admin (owner decisions 2026-11-20). `stock_levels.low_stock_at` (each product's own level, default 5), private `stock_movements` (every change with its reason, note, administrator or order; one row per signed request). Triggers record an order's units (`order_lines` insert) and a cancellation's return (`orders` status to cancelled). service_role-only `admin_list_inventory` (out, then low, then the rest), `admin_get_inventory` (with the last 100 movements), `admin_adjust_stock` (add / remove / set with a fitting reason; never below zero), `admin_set_low_stock`. Replaces `admin_set_product_stock` (0016) to record a correction, and `admin_country_summary` (0009) to count low stock with each product's level. History starts when this runs. Requires 0004, 0006, 0009, 0016. |
| `0018_category_admin.sql` | DRAFT, not applied anywhere: categories and brands from the Central Admin (owner decisions 2026-11-20). Fills the database with the storefront's category list (`packages/country-config`, generated block checked by `tests/taxonomy-sql.test.ts`): names, order, descriptions, every group and subcategory; new rows get ids made from their slugs (`taxonomy_uuid`), and a name an administrator changed (`edited_at`) is not overwritten when it runs again. `categories.description`, private `category_banners` (one photo per category, 1 MB), and the change log of 0016 takes `category.save`, `category.banner`, `brand.save`. For anon: `public_category_tree()` (active categories, groups and subcategories in order) and `public_category_banner(slug)`. service_role-only: `admin_category_tree` (with product counts), `admin_save_taxonomy` (create or edit a category, group or subcategory; the slug never changes; `shop-by-use` is reserved), `admin_save_brand`, `admin_set_category_banner`, `admin_get_category_banner`. Requires 0001, 0003, 0016. |
| `0019_reports.sql` | DRAFT, not applied anywhere: the Central Admin's Reports (owner decisions 2026-11-20: a sale is a paid order, CSV download). Read only; nothing is stored. service_role-only functions for a period of the country's own days (Africa/Dar_es_Salaam, both ends included, at most 366): `admin_report_sales` (placed, paid, cancelled and open orders, a row per day, by payment method), `admin_report_products` (top products and every category from paid orders' lines), `admin_report_orders` (orders placed by status now and by region; each rider's deliveries given in the period, delivered, failed attempts, cash collected), `admin_report_stock` (out, low, units and value at today's prices now; stock movements in the period by reason; the products that need attention). No customer names, emails, phones or addresses in any report (regions only). Helpers `report_orders_in` and `report_period_ok` are not callable by anyone else. Requires 0004, 0006, 0008 and 0017. |
| `0020_delivery_code_owner_only.sql` | DRAFT, not applied anywhere: security audit 2026-11-21 (F-01, F-07). `customer_delivery_code()` answers only the signed-in owner of the order (`auth.uid()`), no longer the order number plus checkout email or phone, which the rider is shown; the second argument stays and is ignored; `anon` can no longer run it. Tracking by number plus email or phone is unchanged. Also `alter default privileges revoke execute on functions from public`, so a function added later is closed until it is granted; `tests/function-grants.test.ts` lists every function a visitor or a signed-in customer can run. Requires 0008. Run it before relying on delivery codes. |
| `0021_order_quantity_500.sql` | DRAFT, not applied anywhere: owner decision 2026-11-21, up to 500 units of a product in one order line (it was 99). The `order_lines.quantity` check and `place_cod_order()` accept 1 to 500; the function is otherwise the one of 0004 (catalogue prices, stock checked and reserved under a lock, one order per idempotency key) and still runs for signed-in customers only (0015). Run it before deploying the storefront that offers more than 99 units. Requires 0004 and 0015. |
| `0005_customer_avatars.sql` | Private Storage bucket `avatars` (2 MB; JPEG, PNG, WebP) and policies on `storage.objects`: a signed-in customer can create, read, replace and delete only `<their user id>/avatar`. Independent of 0001-0004. |

Money columns (`*_minor`) are integers in the currency's ISO 4217 minor unit:
TZS 28,000 is stored as 2800000.

## Setting up a new Supabase project

Each step is an owner action in the Supabase dashboard or the hosting
settings. Nothing in this repository connects to the project by itself.

1. **Tables and rules.** In the SQL editor, run `0001` to `0005` in order,
   one file at a time. Each file is one transaction: a failure changes
   nothing. `0005` (profile photos) does not depend on the others.
2. **Products.** The storefront shows nothing until the catalogue tables
   have rows. For the SAMPLE catalogue (the one mock mode shows):
   - `pnpm --filter @tronic/database run setup:sql` writes
     `database/out/sample-catalogue.sql` (not committed) and checks it
     against a disposable database;
   - run that file in the SQL editor. It stops, changing nothing, if
     `0004` is missing or the catalogue already has products, categories
     or brands.
   - The prices and stock in it are placeholders. Once step 3 is done the
     storefront takes real Cash on Delivery orders at those prices, so
     replace them with the approved catalogue and price list first, or
     keep the site private until then.
3. **Connect the storefront.** In the hosting settings set `DATABASE_URL`
   to the project's transaction pooler connection string (port 6543) and
   `DATA_SOURCE=database`, then redeploy. Do this last: with
   `DATA_SOURCE=database` and missing tables, catalogue, checkout and
   account pages answer with a server error.
4. **Check.** A category page lists products, a product page opens, and a
   test order placed at checkout appears under Account, My orders.

## Tests (disposable database only)

`pnpm --filter @tronic/database test` applies every migration to a fresh
in-process PGlite database that first receives a Supabase stand-in (roles,
`auth.uid()`, the Storage tables, Supabase's permissive default grants), then checks permissions,
country isolation, money units and order behaviour as the anon and
authenticated roles. Nothing is applied to Supabase or any shared database.
